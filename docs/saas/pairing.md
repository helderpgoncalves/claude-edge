# Pairing devices

Three things have to be linked to one account: the user's machine, their phone,
and their Edge. Each has different input capabilities, and the Edge has almost
none.

The constraint that shapes everything: **the Edge has no camera and no
keyboard.** It cannot scan a QR code and it cannot have a token typed into it.
So the Edge is never paired directly — it is paired *through* the phone.

## The flow

```
1. machine     claude-edge login          →  device-code flow in a browser
2. phone       open the PWA, sign in      →  ordinary web login
3. phone+machine  set a session passphrase →  derives Ks on both, never sent
4. Edge        Garmin Connect app settings →  paste from the phone's clipboard
```

Steps 1–3 establish the account and the encryption. Step 4 is the awkward one.

## 1. The machine — device code

The user runs a CLI on a machine that may be headless. Asking them to paste a
token into a terminal is bad practice: it lands in shell history, in scrollback,
and in any terminal-recording tool they happen to run.

The device authorisation grant (RFC 8628) avoids all of that — the same flow a
smart TV uses:

```
$ claude-edge login

  Open  https://claude-edge.dev/link
  Enter code:  BQTK-3H9F

  Waiting…
```

The user opens that on any device where they are already signed in, types eight
characters, and confirms. The CLI polls and receives a token it stores in the
OS keychain.

- The code is short-lived (10 minutes) and single-use.
- It is drawn from an unambiguous alphabet — no `0`/`O`, no `1`/`I`/`l`.
- Rate-limited hard: a four-character-pair code has a small space, so brute
  force must be impossible rather than merely slow.
- The confirmation screen names the machine and its IP, so a user who did not
  initiate it can decline.

## 2. The phone — ordinary login

The PWA is a web page. The user signs in with email, password, and TOTP. There
is nothing exotic here and nothing exotic is warranted.

## 3. The session passphrase — where privacy is actually established

This is the step that makes the relay honest, and it is worth being explicit
about because it is the only part the user has to understand.

When the machine and the phone are both linked, the user sets a **session
passphrase**. It is entered on both, and from it each side derives the same key:

```
Ks = Argon2id(passphrase, salt = account id, ...)
```

- The passphrase is **never transmitted**. We never see it, and we never see
  `Ks`.
- Terminal content is encrypted with `Ks` before it reaches the relay.
- If the user forgets it, we cannot recover it. Their sessions become
  unreadable and they set a new one. That is the cost of the guarantee, and it
  should be said plainly in the UI rather than buried.

The alternative — us generating and holding the key — would be more convenient
and would make the privacy claim false. Not worth it.

## 4. The Edge — the hard part

The Edge needs a server URL and a token in its Connect IQ settings. It has no
camera, no keyboard, and no clipboard of its own.

### Options considered

**QR code.** The obvious idea, and it does not work: the Edge has no camera.
Nothing on the device can read one.

**Bluetooth pairing from the phone.** Connect IQ has no API for an app to write
its own settings from a paired phone. Settings are owned by Garmin Connect
Mobile.

**Typing on the device.** `WatchUi.TextPicker` exists and works, but a 43
character token entered with seven buttons is genuinely unusable — several
minutes, and one mistake means starting over.

**A short pairing code, exchanged for a token.** This is the answer.

### The design

The Edge settings hold a **short pairing code**, not a token:

```
Garmin Connect → Claude Edge → Settings
  Pairing code:  BQTK-3H9F
```

Eight characters, generated by the PWA, valid for ten minutes. Short enough to
read off the phone and type once — or, far more commonly, to copy from the PWA
and paste into the Garmin Connect field, since both are on the same phone.

On first run the Edge exchanges it:

```
POST /api/v1/pair   { code: "BQTK-3H9F", device: "edge540" }
  → { token: "...", relay: "https://relay.claude-edge.dev" }
```

The device stores the returned token in `Application.Storage` and never uses
the code again. The code is invalidated server-side on first use.

Properties worth noting:

- The user copies eight characters instead of forty-three, on a phone, between
  two apps that are both already open.
- A leaked pairing code is useless after ten minutes or one use.
- The long-lived token never appears on screen and is never typed.
- Each device gets its own token, so an Edge can be revoked without touching
  the phone.

### Why not skip the code and have the phone push settings

Because Connect IQ does not permit it. App settings are written by Garmin
Connect Mobile, and there is no API for a third-party app to set them. This is
a platform limit, not a design choice.

## Revocation

Every paired thing is listed in the web app with its last-seen time, and can be
revoked individually:

```
Machines
  macbook-pro          last seen 2 minutes ago         [revoke]
  home-server          last seen 3 days ago            [revoke]

Devices
  iPhone (PWA)         last seen 1 minute ago          [revoke]
  Edge 540             last seen 4 minutes ago         [revoke]
```

Revoking invalidates that token immediately. Changing the account password
revokes everything, which is the behaviour people expect and rarely get.

## Security notes

**The pairing code is a bearer credential for ten minutes.** Everything about
its handling follows from that: single use, short expiry, unambiguous alphabet,
aggressive rate limiting, and invalidation the moment it is redeemed.

**The Edge token cannot approve prompts by itself.** It is scoped to the
account's session, and the approval path still requires the screen-hash binding
that the single-user design already enforces. A stolen Edge is a stolen
read-mostly view, not a shell.

**A lost Edge is handled by revocation, not by a device wipe.** The token lives
in app storage that a thief could in principle extract; revoking from the web
app makes it useless regardless.

## Open questions

- **Should the Edge token expire?** A rolling expiry with silent renewal is
  more secure but fails badly if the device is offline for a month, which is
  entirely normal for a bike computer over winter.
- **Multiple Edges per account.** Straightforward, but the session picker on the
  device needs to make clear which machine it is talking to.
- **Pairing without a phone at all.** Currently impossible: Garmin Connect
  Mobile is the Edge's only network path.
